## Уточнения к текущему коду

- Python: документация говорит 3.9+, но `llm.py` использует `str | None` без отложенного вычисления аннотаций; текущему коду требуется как минимум 3.10. Совместимость всех зависимостей проверяется отдельно.
- Локально работают интерфейс и движок. Приложение обращается к HH и отправляет текст вакансии и резюме выбранному LLM; фраза «полностью локально» не означает отсутствие передачи данных.
- Поддерживаются Anthropic, OpenAI, YandexGPT и Gemini. LLM используется и для скоринга названия, и для письма. Без доступного LLM работают эвристика и шаблон.
- `.env` находится в корне проекта, а не внутри `state/`.
- API-путь `run.py` содержит отправку через `/negotiations`, а не только поиск. Доступность отправки на стороне HH не проверялась.
- `setup.sh` также обновляет pip и создаёт `.env` из примера, если файла ещё нет. Размеры окружения и браузера в старой инструкции — приблизительные.
- Закрытие окна сервера не является гарантированной штатной остановкой дочернего прогона: код не содержит соответствующего обработчика завершения сервера.
- Новый LLM-ключ применяется при загрузке конфигурации новым процессом. Уже работающий прогон продолжает использовать загруженный ключ. Перезапись файла не отзывает ключ у провайдера.
- Список моделей и сведения о доступности сервисов в регионах в старых документах не проверялись на актуальность.

## Подтверждённые ограничения для планирования MVP

1. Пробный режим отключён: `config.DRY_RUN=False` независимо от `.env`. Указания README о безопасном shadow-запуске устарели.
2. Лимит откликов считается за прогон, а не за календарные сутки.
3. Успех отклика определяется по кликам и наличию элементов без подтверждения от HH. Выбор резюме и заполнение письма не гарантированы.
4. `seen.json` сохраняется в конце; принудительная остановка или ошибка могут потерять новые отметки. ID добавляется до проверки лимита и отправки, поэтому часть неотправленных вакансий может исключаться из повторных прогонов.
5. Журнал решений очищается при новом браузерном прогоне. Это не полная история откликов.
6. Защита от одновременных запусков не атомарна. PID не проверяется на принадлежность процессу проекта. Сброс истории доступен во время прогона.
7. Отдельного обнаружения капчи и истёкшей сессии нет. Наличие файла сессии не подтверждает действительный вход.
8. `/api/runlog` читает `state/run.log`, хотя фоновый процесс пишет `state/run_web.py.log`; счётчики не включают `applied_no_letter`.
9. HARD-фильтры применяются к карточке до загрузки подробностей; стоп-слова проверяются только в заголовке. Скоринг оценивает название, а не соответствие опыта кандидата описанию вакансии.
10. Зависимости не закреплены точными версиями. Настройки и файлы состояния не имеют полноценной валидации и атомарной записи.

Эти пункты — результаты чтения кода, а не разрешение на исправления или запуск реальных откликов.

## Точечная адаптация LIVE DOM (9 сентября 2026)

Текст вопросов извлекается из подписей/ARIA и ближайшего отдельного контейнера,
без обязательной вступительной фразы. Неопределённая обязательность хранится как
`null`: без надёжного ответа такое поле блокирует отправку; пропуск допускается
только при явно определённом `false`. LLM prompt и evidence validation не изменены.

Dropdown в блоке «Резюме для отклика» поддерживается при наличии единственного
триггера и однозначных ID в ссылках `/resume/<id>` или `data-resume-id`.
Список связывается через `aria-controls`/`aria-owns` либо локальный `role=listbox`;
вариант выбирается только по точному ID, выбранное значение проверяется повторно.
Названия резюме не используются для сопоставления. Другой DOM остаётся безопасной
остановкой. Проверка выполнена на искусственном HTML, не на авторизованном HH.

Поддерживаются оба переключателя письма: `vacancy-response-letter-toggle` и
`add-cover-letter`. При отсутствии формы сохраняется безопасная диагностика
элементов, заголовков и URL без query. Для неизвестных modal сохраняются метаданные
и ограниченные фрагменты предупреждения; произвольный текст формы исключается.
Диагностика dropdown содержит ID до/после и ID вариантов, без текстов резюме.
Настройки matching, предупреждений и подтверждения отправки не изменены.

Инвариант остаётся обязательным: `selected_resume_id` текущего прогона должен
совпасть с повторно подтверждённым ID резюме в форме HH, иначе submit запрещён.
Для standalone response form механизм переключения пока не установлен. Сохраняются
только безопасные structural snapshots и mutation metadata; экспериментальный
fallback с клавишей Enter удалён, поскольку реальные прогоны не подтвердили его пользу.

## Early DOM routing (10 сентября 2026)

Перед этой правкой создан локальный checkpoint `5ebd746` со всеми текущими
SAFE/LIVE-возможностями, без приватных данных. Новые изменения не заменяют flow.

Однозначная видимая активная кнопка `relocation-warning-confirm` распознаётся
без обязательного dialog/modal. Подтверждение выполняется один раз; обработка
language warning и запрет автоматического продолжения неизвестных предупреждений
сохранены. Неизвестное состояние по-прежнему имеет прежний timeout.

Известная кнопка submit позволяет распознать контейнер отклика даже без HTML form:
используется окружающий dialog или ближайший блок с известными controls письма.
После распознавания сразу выполняются прежние этапы questions → resume → letter →
validation → submit → confirmation. Для контейнера без form поля перечисляются
локально и проходят те же проверки; наличие кнопки не означает успешный отклик.

Проверки выполнены на искусственном DOM с полностью локальной имитацией HTTP и LLM.
Это не подтверждение работоспособности на всех вариантах реального HH.

## Resume / final request после run 1343a7b7

В сохранённом run у трёх страниц вопросов history содержит `questions=[]`, хотя
page-wide snapshot содержит поля. Это не доказательство успешного заполнения:
ранний routing выбирал нижний блок вместо всей HTML-формы. Теперь при наличии
формы используется весь её scope, а визуальное расположение после resume heading
не исключает вопросы. Prompts/answer/evidence pipeline сохранены.

Выбор resume получает подробные reason_code: trigger отсутствует, popup не открылся,
exact target не найден, selected value не изменился. Поиск popup учитывает отдельный
видимый drop-base с radio даже без ID в текстовом содержимом самого wrapper.
После реальной попытки открытия/выбора, если DOM не даёт окончательного доказательства,
разрешается дойти до submit с `resume_verification=payload_pending`. Это не разрешение
отправки: перехватчик обязан подтвердить exact resume/vacancy до пропуска запроса.
Несовпадение/отсутствие ID блокирует запрос. После пропуска записывается exact_payload.

Проверка запроса поддерживает JSON, URL-encoded и multipart, известные response paths,
`/negotiations` и POST в точный `/vacancy/<current id>`; неизвестный endpoint не
пропускается. Если поле письма присутствует в payload, оно сравнивается с prepared
letter; в остальных случаях сохраняется обязательная DOM-проверка перед submit.
Добавлены safe network metadata: path без query, method, encoding, identity field names,
resume ID/совпадение, letter presence/совпадение, armed/action/reason, HTTP status и
ограниченный redirect path. Payload, cookies, headers и текст письма не логируются.
Служебные POST разрешены только для явно ограниченного списка read-only endpoints;
неизвестные writes остаются заблокированными и диагностируются.

У АРСфин и Айвонту в старом run были request_sent=false/blocked=true, но URL и тело
не сохранялись. Поэтому формат/endpoint конкретной старой блокировки доказать нельзя.
Новые варианты покрыты локальными тестами, не проверены на реальном HH.

## Transient submit / questions после run fa2313ae

В run известные multipart-запросы popup блокировались с
`submit_payload_resume_missing`. Аналитические POST затем затирали итоговый detail
код. Теперь application_requests сохраняются отдельно от ограниченной аналитической
ленты, а detail берётся из связанного application request. Поддержан также точный
alias resume_hash (без ослабления проверки значения). Старый лог не содержит имени
нераспознанного resume-поля, поэтому нельзя утверждать, что это был именно данный alias.

Точная видимая ошибка «Произошла ошибка, попробуйте ещё раз» ищется в response scope
или role=alert, не произвольным поиском по странице. Единственный retry допускается
только если ни один application request не был разрешён, отсутствуют success/already
markers, submit видим/активен, resume повторно подтверждён, письмо совпадает и ответы
прочитаны обратно. Известный payload mismatch запрещает retry. Sent latch ставится
до пропуска запроса и не сбрасывается между кликами: второй application request
не выпускается. После попытки submit закрытый guard сохраняется до закрытия контекста,
чтобы запоздавшие запросы не ушли после возврата функции. При возможной отправке
retry отсутствует, статус остаётся submission_unknown.

Language warning до формы обрабатывается прежним способом. Если известный language
dialog появляется после уже наблюдавшегося write-запроса, его кнопка больше не
нажимается повторно: приложение ждёт только явный HH success/applied marker. Без
него результат остаётся submission_unknown, а не обычным manual.

Question pipeline не меняет prompts/evidence. Скрытый вспомогательный textarea больше
не обрывает поиск заголовка radio-группы. JSON-ответ допускает полную Markdown-обёртку
```json, но не исправляет/додумывает повреждённый JSON или evidence. В реальном логе
ИнфоТек имел пустой question, HR-tech — корректный question и llm_invalid_json; raw
LLM response не сохранён, поэтому причина конкретного malformed ответа неизвестна.

99 локальных тестов прошли, включая full language→questions→resume→letter→transient
без request→один retry→request→confirmation, повторную transient-ошибку и запрет retry
после разрешённого запроса. Реальный HH/LLM не запускались.

## LIVE: DOM разрешает submit, сеть наблюдает (после run 8fea5920)

Этот раздел заменяет описанные выше требования exact_payload/payload_pending и
блокировки неизвестных запросов ПОСЛЕ финальной проверки формы.

В последнем run 8fea592061e34f69b7d1dbf703fe7f4c шесть вакансий
137171439, 137165344, 136621119, 136978941, 136097452, 137174454 дошли
до клика с dom_verified, проверенным письмом и enabled submit. Все шесть запросов
/applicant/vacancy_response/popup наш guard заблокировал с submit_payload_letter_mismatch
при resume_matches=true. Сохранённые данные не объясняют различие текста payload;
оно больше не является разрешающей проверкой LIVE.

До final click обязательны вопросы/readback, exact ID выбранного резюме из текущего
DOM/state HH, письмо/readback, валидность формы и enabled submit. Локальный title→ID
не является разрешающей проверкой.
Payload-only подтверждение резюме удалено. Durable apply_submit_started записывается
перед кликом, а не внутри сетевого перехвата. Ошибка записи запрещает клик.
После этого LIVE пропускает браузерные запросы независимо от endpoint, payload и
диагностических совпадений. До проверки формы ранние writes по-прежнему блокируются,
кроме известных read-only сервисов: quick apply не должен отправить чужое резюме.
SAFE возвращается до работы с браузером; подтверждение каждого LIVE-run сохранено.

Success требует свежего явного HH success/applied marker. Любой наблюдавшийся
неслужебный write после разрешения трактуется консервативно как возможная отправка:
без HH confirmation — submission_unknown, автоматического retry нет. Это может
запретить retry при постороннем write, но не запрещает первый разрешённый submit.
Без request единственный retry допускается только при точной видимой transient-ошибке
и повторной проверке формы. Известный отдельный language warning до наблюдавшегося
write допускает один подтверждающий клик; после write повторный submit запрещён.
После возврата собственный route снимается: разрешённый LIVE не блокирует поздние
запросы браузера.

## Диагностика recovery и открытия resume dropdown

Recovery сохраняет только metadata: recovery_candidates_count, recovery_best_token_count,
recovery_best_coverage (отношение числа токенов запроса к длине фрагмента, как в gate),
recovery_order_preserved, recovery_extra_tokens_count, recovery_extra_tokens_allowed,
recovery_failure_reason. Ближайший кандидат для диагностики выбирается по покрытию
токенов запроса, затем фрагмента; этот рейтинг не влияет на существующее принятие.
Причины: too_few_tokens, query_tokens_missing, disallowed_extra_tokens,
coverage_below_threshold, token_order_failed, ambiguous_best_match, no_candidate,
strict_validator_failed. Тексты/токены источников не сохраняются.

В resume_dropdown_diagnostics.dom_snapshots добавлены before_click,
immediately_after_click, 500ms, 1500ms и wait_finished (около 3000ms при неоткрытии).
Если варианты найдены раньше, ожидание не продлевается ради снимков. Снимки содержат
trigger tag/role/aria-expanded/controls/owns, active element tag/role, visible counts
listbox/menu/option/resume/dropdown/popup, overlay/dialog count, metadata ближайших
контейнеров и новых изменённых контейнеров с интерактивными элементами, количество
clickable option-like элементов, dom_changed и elapsed_wait_ms. MutationObserver
фиксирует факт изменений; тексты и значения полей не экспортируются. Идентификаторы
ограничены и проходят очистку. Observer отключается в finally.

Пороги evidence, dropdown selectors/выбор/click и timeout не изменены. Диагностика
использует прежний цикл ожидания. Проверяются только два целевых теста: причины recovery
и отсутствие приватного текста в DOM metadata. Реальные HH/LLM и полный suite не запускаются.

Для следующего resume-switch failure сохраняются также безопасные признаки найденного
resume trigger и его видимых интерактивных потомков: role, data-qa, aria, disabled и
class signature. После click фиксируются число и расположение exact target option по
`data-qa=magritte-select-option-<resume_id>` относительно trigger/page portal. Названия,
тексты, контакты и содержимое резюме не сохраняются. Это наблюдаемость, а не новый
selector или fallback.

Перед click и сразу после него snapshots также содержат hit-test центра resume-card:
геометрию, безопасные признаки `elementFromPoint`, отношение элемента к card и, только
для внешнего элемента, короткую цепочку родителей. Это позволяет отличить click по card
или её потомку от перекрытия другим слоем без сохранения текста DOM.

## Подключения ИИ и failover (17 сентября 2026)

Общий путь: `decide.score` / `decide.cover_letter` / `application.answer_question`
→ `llm.generate` → run-scoped `Router` → `llm_provider.execute`.
Prompts, score/JSON и evidence gates остаются в task modules. Локальные ответы,
включая Telegram выбранного резюме, по-прежнему обходятся без LLM.

В блоке «Подключения ИИ» доступны список, добавление и включение/выключение.
После сохранения поле ключа очищается; API возвращает только `credential_configured`.
Изменения применяются со следующего прогона. Редактирование/удаление/перестановка
в UI пока отсутствуют; заменить подключение можно добавлением нового и отключением старого.

Хранилище — `private/llm_connections.json`, версия 1, массив `connections`.
Каждая запись: стабильный `id`, `provider`, `model`, `enabled`, `credential`, `folder_id`.
Порядок массива задаёт приоритет; новые подключения добавляются в конец.
Ключи локальны, файл не шифруется, записывается атомарно с правами 0600;
symlink в пути отвергается. `private/` уже исключён из Git. Runtime-недоступность
никогда не записывается как `enabled=false`. Не включать этот файл в архивы/публикации.

Если файла нет, `LLM_PROVIDER`, `LLM_MODEL`, `LLM_API_KEY`, `YANDEX_FOLDER_ID`
представляются одним connection `legacy`. Первое сохранение в новом UI переносит
его в список и добавляет новую запись, не изменяя `.env`. После этого список —
источник LLM-настроек; изменения старых LLM-полей `.env` его не переопределяют.
Явно пустой список не возвращает legacy автоматически. Повреждённый список
блокирует загрузку router; ключи и сырой JSON не включаются в ошибку.

Routing: текущее доступное подключение → оставшиеся с тем же provider/model
→ остальные по сохранённому порядку. Disabled, пустой credential и Yandex без
folder ID пропускаются. Сохранены HTTP-контракты Gemini, Anthropic, OpenAI, YandexGPT.
Используются только существующие текстовые adapters; работоспособность конкретного
имени модели и качество другого provider offline-тестами не подтверждаются.
Все прежние task validation gates остаются обязательными. Невалидный matching JSON
не является основанием ослабить validation или автоматически перебрать провайдеров.

Gemini HTTP 429 классифицируется по `google.rpc.QuotaFailure.violations[].quotaId`:
известные GenerateRequests PerDay / PerMinute и GenerateContentInputTokens PerDay /
PerMinute (с известными FreeTier/PaidTier суффиксами). Дневной тип имеет приоритет
при нескольких нарушениях. Неизвестные идентификаторы/форматы и human-readable
message не используются как доказательство дневной квоты; результат — unknown.
В диагностике остаются нормализованные `quota_types`, а не произвольные идентификаторы,
quota dimensions, response body, URL или headers. Основа формата:
[Google RPC error details](https://github.com/googleapis/googleapis/blob/master/google/rpc/error_details.proto),
[Gemini rate limits](https://ai.google.dev/gemini-api/docs/rate-limits).

Централизованная policy в `llm.py`:

- Подтверждённая дневная квота: 0 повторов, unavailable до конца прогона, failover.
- RPM, TPM и unknown 429: максимум 1 повтор (2 попытки всего на подключение).
- Без retry metadata: задержка 2 секунды.
- `RetryInfo.retryDelay` и `Retry-After`: выбирается большая корректная задержка;
  минимум ожидания 1 секунда, максимум 30 секунд.
- Если provider просит более 30 секунд, не повторяем раньше срока: сразу failover,
  подключение unavailable до конца прогона. Reset timestamp не выдумывается.
- 401/403, 5xx, прочие HTTP, transport и malformed provider envelope различаются;
  для них дополнительных повторов нет, используется failover.

После исчерпания usable connections возникает `LLMUnavailable`. Она проходит через
matching, письмо и вопросы (включая optional) до run control. Прогон получает
`STOPPED / llm_infrastructure_unavailable`, текущая вакансия — manual review;
следующие вакансии не обрабатываются. В terminal-диагностике есть безопасные
provider/category/status/task/attempt metadata. После нового прогона availability
сбрасывается. Сохранённые enabled-флаги не меняются.

Privacy boundary учитывает все загруженные credentials, включая disabled и резервные,
и проверяет вход/выход общего LLM facade. Сырые requests exceptions не передаются
в terminal exception. На завершении HTTP-ветки остаётся только безопасная классификация.

Проверки: `test_llm_connections`, `test_llm_ui` и связанные targeted task tests
используют искусственные credentials, временное storage, подмену HTTP/HH и локальный
Chromium без внешних запросов. Fixtures вопросов требуют exact evidence, а варианты
radio/select передают в LLM только защищённые aliases вместо raw DOM values. Реальные
provider calls и HH не запускаются.

Безопасная ручная проверка: открыть настройки без запуска прогона, увидеть legacy A,
добавить B, проверить отметку «ключ сохранён» и пустое поле ключа, отключить/включить B
и перезагрузить страницу. Это проверяет persistence без расходов API. Даже SAFE-прогон
может обращаться к LLM: для проверки только настроек его запускать не нужно.

Подключения, routing, privacy boundary и UI покрыты offline-тестами с
искусственными credentials, HTTP и локальным Chromium. Реальный provider failover
между сохранёнными подключениями пока не подтверждён и требует отдельного
контролируемого прогона.

## Role alignment matching (18 сентября 2026)

Один matching-вызов LLM теперь получает отдельно search intent текущего прогона,
название выбранного резюме из точной записи `state/resumes.json`, подтверждённый
опыт из резюме и полную вакансию. Search intent задаёт контекст поиска и не служит
списком разрешённых названий. Если для выбранного ID нет единственного безопасного
названия, matching не выполняется и вакансия остаётся на ручной проверке.

Ответ обязан содержать классификацию фактической роли вакансии
(`primary_function`, `functional_scope`, `seniority`, `accountability`),
`role_alignment`, причину и evidence по вакансии. `score` сохранён как оценка
подтверждённых возможностей и должен в точности совпадать с `capability_score`.
Неполный или неверный ответ не проходит validation и не создаёт готовый отклик.

`aligned` продолжает существующий путь remote/score/письмо. `adjacent` и `unclear`
требуют ручной проверки, `functional_mismatch` блокирует подготовку отклика независимо
от capability score. Оригинальный результат matching остаётся в `matching_result`,
поэтому итог application не затирает его причину. В ленте для невыравненных ролей
показывается короткая причина.

Проверки используют только искусственные вакансии и подменённый LLM: проверены
контракт входов/выхода, отсутствие metadata title, строгая validation, сохранение
результата и запрет письма/submit при `functional_mismatch`. Реальные HH и LLM
для этой правки не запускались.

Реальный CCO-прогон подтвердил, что gate отсеивает многие вакансии другой
функциональной направленности. Это не завершает calibration: смежные роли и
отраслевые различия по-прежнему требуют отдельной настройки на размеченных решениях.
