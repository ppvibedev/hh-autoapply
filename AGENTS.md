# Правила работы над HH Auto Apply

## Общение и границы задачи

- Объясняй решения по-русски, простыми словами. Пользователь осваивает Git/GitHub.
- Перед изменениями изучи связанные исходники и документацию. Различай фактическое поведение, предположения и планы.
- Выполняй изменения в рамках запроса пользователя; не добавляй попутный рефакторинг.
- Работай в режиме точечной разработки: одна задача — один доказанный failure. Не проводи общий аудит репозитория, не расширяй scope и не делай попутный рефакторинг.
- Текущий этап: активная точечная доработка LIVE MVP по результатам реальных прогонов. Уже работающие и подтверждённые LIVE-ветки не меняй без доказанного regression/failure.
- Перед исправлением проверяй только файлы и данные, относящиеся к этому failure. При недостатке данных остановись и сообщи, чего именно не хватает; не угадывай selectors, причины или поведение.
- Для изолированного изменения запускай targeted tests вместо полного набора тестов. В конце давай краткий отчёт: причина, изменение, проверка и ограничения.
- 7 сентября 2026 года пользователь разрешил создать приватный репозиторий GitHub и загрузить текущий промежуточный снимок MVP без секретов. Это разрешение на первоначальную копию; дальнейшие публикации выполняй в рамках явно согласованной задачи.

## Приватные данные

- Никогда не коммить и не отправляй в GitHub `.env`, `state/`, сессии HH, cookies, токены, API-ключи, пароли и credentials, включая их копии.
- Не выводи секреты и содержимое приватных файлов в ответы, логи, документацию или тестовые данные. Для аудита используй пути, метаданные и обезличенные результаты.
- `.env.example` должен содержать только безопасные примеры и пустые значения для секретов.
- `.gitignore` — отдельный механизм Git, а не замена этим правилам. Перед коммитом проверяй фактический список подготовленных файлов; исключения не очищают старую историю и не защищают обычные архивы.
- Недостающие исключения сначала покажи пользователю и согласуй; не ослабляй существующую защиту.
- Не удаляй и не сбрасывай пользовательское состояние без явного запроса. `cleanup.sh` удаляет `.env` и `state/`.

## Безопасность проверок

- Не запускай реальные отклики как способ тестирования. Использование авторизованной сессии, отправку откликов и передачу приватного резюме внешнему LLM согласовывай явно в рамках конкретной задачи.
- Не считай значение из `.env` единственной LIVE-защитой: текущий browser path дополнительно требует одноразовое подтверждение конкретного LIVE-run. В тестах всё равно используй mock и запрет внешней сети.
- Предпочитай статические проверки и тесты на искусственных данных с имитацией HH и LLM. Не используй реальные ключи и cookies в тестах.
- Проверяй изменения соразмерно риску. В отчёте указывай, что проверено, а что не запускалось.

## Git и ветки

- Read-only проверки статуса, веток, истории и remotes допустимы; скрывай секреты, если они встречаются в адресах или выводе.
- `main` — стабильная версия. Существенные функции и крупные исправления делай в отдельных ветках; перед созданием коротко объясни назначение ветки.
- Не создавай новые ветки автоматически; создавай ветку только по прямому запросу пользователя.
- Push, merge в `main`, rebase, удаление веток, публикация и checkout/reset с риском потери данных требуют явного разрешения пользователя. Не уничтожай чужие незакоммиченные изменения.

## Ориентиры по проекту

- Основной путь: `webapp.py` → `run_web.py` → `hh_web.py` / `browser.py`; интерфейс — `web/index.html`.
- Общие решения: `decide.py`; LLM-клиенты: `llm.py`; настройки: `config.py` / `envfile.py`.
- Дополнительный API-путь: `run.py` / `hh_client.py`; он тоже содержит реальную отправку.
- При локальном bugfix читай только релевантные разделы `docs/PRODUCT_LOGIC.md`, индекс `docs/README.md` и связанные исходники. Документы в `docs/archive/` — историческая справка, которую нужно сверять с кодом, а не разрешение запускать приложение.
- При согласованных изменениях поведения обновляй относящуюся к ним документацию. Не описывай предполагаемую защиту как уже работающую.

## Поддержка канонической документации

- `docs/PRODUCT_LOGIC.md` — каноническое owner-facing описание наблюдаемого поведения. Production code и regression tests являются источником проверки этого описания.
- Любое изменение observable product behavior должно в том же commit: проверить `PRODUCT_LOGIC.md`, обновить затронутые разделы при изменении semantics и добавить/обновить regression test.
- Observable behavior включает settings, decision order, filters, statuses, SAFE/LIVE, matching, application, resume, questions, submission, Stop, persistence/history и видимую пользователю UI-semantics.
- Для refactor, diagnostics-only и внутренней оптимизации без observable change обновление `PRODUCT_LOGIC.md` не обязательно. В итоговом отчёте укажи `PRODUCT_LOGIC reviewed: no observable change` либо `PRODUCT_LOGIC updated: <sections>`.
- Не описывай `PROPOSED`, `HISTORICAL` или `UNKNOWN` как `CURRENT`.
- Проверяй согласованность `PRODUCT_LOGIC ↔ production code ↔ regression tests` перед major LIVE/checkpoint либо примерно после 10 commit, меняющих поведение — что наступит раньше.
